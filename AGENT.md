## Key Engineering Decisions

### 1. Decoupled Client-Server vs. Next.js Monolith
- **Decision**: Keep `client/` (Next.js) and `server/` (Express) completely decoupled rather than writing backend API routes inside Next.js App Router (`app/api/*`).
- **Rationale**:
  - Independent scalability: The backend API can be scaled, containerized, or deployed to different infrastructure (e.g. AWS ECS or Render) without redeploying the static frontend.
  - Portability: External clients (mobile applications, third-party webhook integrations, Zapier, etc.) can consume the Express API without being coupled to Next.js server runtime constraints.
  - Framework independence: Prevents vendor lock-in to Next.js server runtime features (e.g., edge middleware limits, serverless database connection exhaustion).

---

### 2. Layered Architecture (Controller-Service-Data)
- **Decision**: Enforce a strict four-layer architecture on the backend:
  $$\text{Route} \longrightarrow \text{Validation Middleware} \longrightarrow \text{Controller} \longrightarrow \text{Service} \longrightarrow \text{Prisma}$$
- **Rationale**:
  - Separation of Concerns: Controllers only manage HTTP requests, status codes, and formatting. Services contain pure business logic and database queries.
  - Testability: Services can be unit-tested independently by mocking the Prisma client.
  - Maintainability: Database query logic is isolated from routing logic.

---

### 3. Dual-Layer Validation with Zod
- **Decision**: Implement Zod validation on both the client (pre-flight form submission) and the server (middleware before controllers).
- **Rationale**:
  - **Client-Side UX**: Gives users immediate, sub-millisecond feedback on malformed emails or empty fields without triggering network latency.
  - **Server-Side Security**: Enforces zero-trust input sanitization. Direct API requests (via Postman, cURL, or malicious actors) are rejected with detailed `400 Bad Request` messages before touching the database.

---

### 4. TanStack Query v5 for Async State Management
- **Decision**: Use `@tanstack/react-query` with Axios rather than standard `useEffect` + `fetch` or Redux/Zustand.
- **Rationale**:
  - `placeholderData: keepPreviousData`: Enables seamless pagination where current page data remains on screen while the next page fetches in the background (no UI flicker).
  - Automatic Cache Invalidation: On `createLead` or `updateLeadStatus`, calling `queryClient.invalidateQueries({ queryKey: ["leads"] })` automatically refetches active queries, ensuring data consistency across tabs and components.
  - Reduced boilerplate: Handles loading, error, refetching, and deduping out of the box.

---

### 5. Prisma ORM v7 with `@prisma/adapter-pg`
- **Decision**: Use Prisma v7 with native PostgreSQL connection adapter.
- **Rationale**:
  - Provides end-to-end type safety from database columns directly into TypeScript interfaces.
  - Declarative schema migrations with automatic SQL generation (`prisma migrate dev`).
  - `@prisma/adapter-pg` provides high-performance connection pooling and compatibility with modern server environments.

---

### 6. Offset Pagination vs. Cursor Pagination
- **Decision**: Use `skip` and `take` offset pagination with page count calculation.
- **Rationale**:
  - For a sales CRM with hundreds to tens of thousands of leads, users expect classic pagination controls (jumping to page 1, 2, 5, etc.) and knowing the total count of matching records.
  - Cursor-based pagination does not easily support arbitrary page navigation or total page count computation without auxiliary queries.

---

### Error Normalization Architecture
- **Decision**: Standardize all API error outputs into a uniform JSON structure and parse them on the client using a custom `ApiRequestError` class.
- **Structure**:
  ```json
  {
    "success": false,
    "error": {
      "message": "Validation failed",
      "status": 400,
      "details": [{ "field": "email", "message": "Invalid email format" }]
    }
  }
  ```
